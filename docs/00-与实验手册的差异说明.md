## 为什么要有这份文档

课程决策的演进：最初是「**不改现有实验手册，另建一个统一载体工程**」；
经实机验证发现 3 处"照抄必失败"的缺陷后，改为「**手册直接修订 + 载体工程作参考实现**」。

于是仍然需要一份文档说明：手册与本工程**还有哪些写法不同、为什么**。

如果不说清楚，会变成两种坏结果：
一是学生照手册抄、抄不通，怀疑自己；
二是学生把差异当成"两个都对"，越学越糊。

**所以差异必须显式讲出来，而且要讲清楚"为什么"。** 本文档逐条给依据。
本工程刻意**保留**手册的全部大纲要点覆盖率（见 §5），差异只在"写法与工程规范"层面。

## 1. 【手册缺陷 · 已于 2026-09-21 修订】P3 只扫 controller 包，`@Autowired UserService` 会失败

> **修订状态**：✅ 已修（勘误编号 E-02）。手册 P3 步骤 1 现已包含 `context-param` + `ContextLoaderListener`，
> 并新增 `src/main/resources/applicationContext.xml` 扫描 service 包。以下为问题成因记录。

### 手册原状（`2627.1_260824` 版）

- 手册 P3 步骤 1② 的 `springmvc-servlet.xml`：

```xml
<context:component-scan base-package="com.example.controller"/>
```

- 手册 P3 步骤 3 又要求学生：「把校验逻辑抽到 Service 层（加注解）」，
  给出 `@Service public class UserServiceImpl implements UserService`，
  并把 Controller 改为 `@Autowired private UserService userService;`

### 问题

`component-scan` 的范围是 `com.example.controller` **及其子包**，
而 `UserServiceImpl` 在 `com.example.service.impl` —— **不在扫描范围内**。

于是 `UserServiceImpl` 从未被注册成 Bean，Controller 装配时直接抛：

```
NoSuchBeanDefinitionException: No qualifying bean of type
'com.example.service.UserService' available
```

即：**手册 P3 步骤 1 与步骤 3 互相矛盾，照做的学生一定卡在这里。**

### 本工程怎么改

采用 Spring 官方推荐的**双容器**结构，各扫各的包、互不重叠：

| 配置文件 | 容器 | 扫描范围 | 管什么 |
|---|---|---|---|
| `applicationContext.xml` | Root（父） | `com.zjtec.admin.service` | Service、DAO、数据源 |
| `springmvc-servlet.xml` | MVC（子） | `com.zjtec.admin.web` | Controller、视图解析 |

配套在 `web.xml` 里加 `ContextLoaderListener` 加载 Root 容器。
子容器能找到父容器的 Bean，所以 Controller 照样能注入 Service。

### 顺带的教学收益（这是白送的一节课）

改完之后可以现场做这个实验：把 Root 的扫描包改成 `com.zjtec.admin.web`，
启动就会报 `NoSuchBeanDefinitionException`。于是问学生：

> 为什么两个配置文件不能扫同一个包？为什么 Controller 能拿到 Service，反过来不行？

这比"照着抄一个 xml"有价值得多，而它本来就是手册那个 bug 暴露出来的知识点。
**换句话说：手册的缺陷，改对了就是一个更好的教学素材。**

## 2. 【手册缺陷 · 已于 2026-09-21 修订】`spring-beans-6.2.xsd` 会让 Spring 联网取 XSD，取不到就启动失败

> **修订状态**：✅ 已修（勘误编号 E-01）。手册全部 7 处（实验二 2 处、实验三 3 处、实验五 2 处）
> 已统一改为无版本号写法。以下为问题成因与实测证据记录 —— **这段证据很适合课上直接展示给学生看**，
> 它解释了"为什么照抄网上的老教程会挂"。

### 手册原状（`2627.1_260824` 版）

手册 P3/P5 的配置里，`xsi:schemaLocation` 写的是**带版本号**的 URL：

```xml
xsi:schemaLocation="
    http://www.springframework.org/schema/beans
    https://www.springframework.org/schema/beans/spring-beans-6.2.xsd
    ..."
```

### 实测证据

Spring 解析 XML 时会先查 jar 包内 `META-INF/spring.schemas` 的离线映射表，
**查不到才联网**。实测 Spring 6.2.19 的映射表内容：

```
spring-beans  (共 60 条)
  http://.../spring-beans-2.0.xsd ~ spring-beans-4.3.xsd     ← 只到 4.3
  https://.../spring-beans-2.0.xsd ~ spring-beans-4.3.xsd    ← 只到 4.3
  http://www.springframework.org/schema/beans/spring-beans.xsd   ← 无版本号 ✅
  https://www.springframework.org/schema/beans/spring-beans.xsd  ← 无版本号 ✅
  （没有 spring-beans-5.x.xsd，没有 spring-beans-6.2.xsd）

spring-mvc    (共 16 条)  同样：只到 4.3 + 无版本号
```

也就是说 `spring-beans-6.2.xsd` **不在离线表里** → Spring 尝试 GET 该 URL
→ 该 URL 实际不提供文件 → 抛异常：

```
Caused by: java.io.FileNotFoundException:
    https://www.springframework.org/schema/beans/spring-beans-6.2.xsd
  → Failed to load ApplicationContext
```

**后果**：机房无外网时 100% 启动失败；有外网时也会白等一次网络超时。
这个问题在 P3 就出现，会一路带到 P5。

### 本工程怎么改

去掉版本号（这也是 Spring 官方文档示例的写法）：

```xml
xsi:schemaLocation="
    http://www.springframework.org/schema/beans
    https://www.springframework.org/schema/beans/spring-beans.xsd
    http://www.springframework.org/schema/context
    https://www.springframework.org/schema/context/spring-context.xsd
    http://www.springframework.org/schema/mvc
    https://www.springframework.org/schema/mvc/spring-mvc.xsd"
```

> 注意命名空间那半（`http://...beans`）**必须与 `xmlns` 完全一致**，
> 能改的只是后面那个 XSD 位置。去掉版本号不会降低校验强度 ——
> Spring 用的 XSD 版本本来就由它自己的 jar 决定，写 `-6.2` 只是"想要"而不是"生效"。

## 3. 【工程规范差异】密码不写死在 XML 里

| | 手册 P5 | 本工程 |
|---|---|---|
| 连接信息位置 | 直接写在 `applicationContext.xml` 的 `<property value="你的密码"/>` | 独立 `jdbc.properties` |
| 改密码 | 要动 XML | 只动 properties |
| 依据 | — | **教材 ch15 就是这么做的**（第 15.3.4 节明确列出 `jdbc.properties`） |

这不是"超纲加料"，而是把教材 ch15 本来就有的工程实践**提前到 P3 建立**。
本工程 P3 就把 `jdbc.properties` 放好（并由启动自检确认"已就位，P4 起启用"），
P4/P5 直接读取，学生不用中途改变习惯。

同理，教材 ch15 的包结构里本来就有 `util`、`config`、`interceptor` 三个包 ——
本工程的 `common` / `config` 包对应其中前两个。

下表记录这次统一的口径，也是本工程定型后的命名约定（可作为后续 P4~P6 的基准）：

## 6. 【超出大纲的部分】明确标注，不计入考核

为让学生看到"一个正经后端项目长什么样"，本工程加了三样东西。
**它们全部标为「拓展 · 不计入考核」，考试不考、进度表不列。**

| 项 | 是什么 | 为什么加 | 对应 ASP.NET |
|---|---|---|---|
| `Result<T>` 统一响应体 | 所有接口返回 `{code, msg, data}` | 没有它，P6 的 AJAX 前端只能靠猜字段名 | `ApiResponse<T>` 包装 / 统一 `IActionResult` |
| 启动自检 `StartupSelfCheckListener` | 启动时打印环境与配置状态 | 实验课最大痛点：跑不起来又不知哪步错 | 启动日志 + HealthChecks |
| Logback 分级日志 | 控制台 + 落文件，可按包调级别 | 出问题能回查，而不是盯着控制台白板 | `ILogger<T>` |

> 课堂建议：花 2 分钟演示一次"故意把数据源写错，看启动自检怎么报"，比讲十分钟理论有用。

## 7. 讲差异时的一句话口径

**第二轮修订之后，手册与本工程在结构、包名、工程名上已经完全一致，"差异"这个话题基本没有了。**

给学生就这么说：

> 你们手上的实验手册和这个工程是**同一套东西**：两个容器，父容器管 Service、子容器管 Controller，
> 包名也一样，都是 `com.zjtec.admin`。手册可以逐字照抄 —— 抄不通就是自己哪一步写错了，
> 不用先怀疑"是不是手册和工程不一样"。

至于几个已经修掉的缺陷（扫描包、XSD 版本号、WEB-INF 直访），可以在课间当"知识彩蛋"讲：

> 手册前一个版本里，这两个地方是错的。第一个错误让 Service 注入不进来，
> 第二个错误在机房断网时会直接启动失败。我把它修好了 ——
> 但你们要记住**它们为什么错**，因为这两个坑，你们以后自己搭项目时百分百会再踩一次。
> 尤其是第二个：网上现在还有大量老教程写着带版本号的 XSD，那些教程的年代还没有 Spring 6。

不遮蔽问题、但也不否定手册 —— 学生能同时学到"怎么写"和"别人为什么写错"。
