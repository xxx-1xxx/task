## 一、先看分层：谁调用谁

```
                 浏览器
                    │  HTTP
                    ▼
   ┌────────────────────────────────────┐
   │  Tomcat 10（外部容器）              │
   │   ├─ Filter  : 编码过滤器           │
   │   └─ Servlet : DispatcherServlet   │  ← web.xml 装配
   └────────────────┬───────────────────┘
                    │ 分发
                    ▼
   ┌────────────────────────────────────┐
   │  web 层   LoginController          │  Root←MVC 子容器，扫描 com.zjtec.admin.web
   │  职责：接参数、调 Service、选视图     │  ❌ 不写业务判断  ❌ 不碰 SQL
   └────────────────┬───────────────────┘
                    │ 接口调用（不认识实现类）
                    ▼
   ┌────────────────────────────────────┐
   │  service 层  UserService(接口)      │  扫描 com.zjtec.admin.service
   │              UserServiceImpl       │  ✅ 业务规则都在这里
   └────────────────┬───────────────────┘
                    │
                    ▼
   ┌────────────────────────────────────┐
   │  mapper 层  UserMapper(接口)        │  P4 启用；SQL 在映射 XML 里
   └────────────────┬───────────────────┘
                    │ JDBC
                    ▼
                MySQL 8.4
```

**实验五考核必答**：把上面这条链路背下来 ——
`DispatcherServlet → Controller → Service → Mapper → MySQL`。

## 二、每个包放什么

| 包 | 放什么 | 不该放什么 | 本工程现状 |
|---|---|---|---|
| `common` | 通用件：统一响应体、应用常量 | 业务逻辑 | ✅ `AppInfo`、`Result` |
| `config` | 配置类、启动自检、监听器 | 业务逻辑 | ✅ `StartupSelfCheckListener` |
| `web` | Controller | SQL、复杂业务判断 | ✅ `LoginController` |
| `service` | 业务接口 | 请求/响应对象、SQL | ✅ `UserService` |
| `service.impl` | 业务实现 | — | ✅ `UserServiceImpl` |
| `entity` | 数据库实体（字段与表对应） | 页面专用字段 | ✅ `User` |
| `dto` | 传输对象（只承载数据，不对应表） | 数据库映射 | P6 引入（`SignupDTO`） |
| `mapper` | 数据访问接口 | 业务判断 | P4 启用 |

## 三、四个"为什么"

### 为什么 `service` 要拆成接口 + 实现？

因为 Controller 只依赖 `UserService` 接口，**不知道背后是谁**。于是：

- P3 的实现是"和常量比对"；
- P5 的实现换成"查 MySQL"；
- **Controller 一行都不用改。**

这就是实验二学的"面向接口编程 / 换实现只改配置"在真实工程里的收益。
如果你觉得这是形式主义，试想：如果 Controller 直接 `new UserServiceImpl()`，
P5 换实现时你要改几个文件？

### 为什么 `mapper` 包里现在只有一份说明文件？

因为 P3 只做 Web 层，还没有数据访问需求。
但**包先留着**，学生一眼能看到"这条链路还有一层没写"，
到 P4 加进去时，位置和职责都是现成的、不需要重新理解结构。

> 顺带一提：Java 的包不能为空（Git 也不跟踪空目录），
> 所以放一个 `package-info.java` 作为占位 + 说明 —— 这是规范做法。

### 为什么 Controller 这么"薄"？

比较两个版本：

```java
// ❌ 反面：全都堆在 Controller 里
@PostMapping("/login")
public String login(String username, String password, ModelMap model) {
    if ("admin".equals(username) && "123".equals(password)) {   // 校验逻辑
        log.info("用户登录：" + username);                        // 记日志
        model.addAttribute("msg", "登录成功");
    } else {
        model.addAttribute("msg", "用户名或密码错误");
    }
    return "result";
}

// ✅ 本工程：Controller 只做三件事
@PostMapping("/login")
public String login(@RequestParam("username") String username,
                    @RequestParam("password") String password,
                    ModelMap model) {
    boolean success = userService.login(username, password);   // ① 调 Service
    model.addAttribute("msg", success ? "登录成功！" : "用户名或密码错误");  // ② 装模型
    return "result";                                           // ③ 选视图
}
```

差别在哪？**校验规则变了（P5 改查库），上面那个要动 Controller，下面这个不用。**
这就是分层的实际意义，不是审美问题。

### 为什么会有 `entity` 和 `dto` 两个包？

- `entity`：**和数据库表一一对应**。`User` 对应 `user` 表，字段就是列。
- `dto`：**只负责传输**。比如 P6 的 `SignupDTO` 只装注册表单的三个字段，
  不对应任何表，也不该有 `id`。

混用一个类会怎样？表加了字段，接口的 JSON 就跟着变；前端加了字段，实体就变脏。
**边界分开，改一边不会牵连另一边。**

## 四、现场可以做的"分层违规"演示

把 `UserServiceImpl` 里的判断直接挪到 `LoginController`，让学生感受：

1. 现在要改校验规则，改哪儿？→ Controller（本该只关心 Web）
2. 现在要给"登录"写单元测试，要不要启动 Spring MVC？→ 要（本该只测规则）
3. 如果以后有第二个入口（比如 App 端）也要登录，规则抄几遍？→ 抄两遍

同一件事再想一遍"如果规则在 Service 里"：
规则只在一处、单测不需要 Web 环境、第二个入口直接复用。

**结论**：分层的回报全在"改得动、测得动、复用得了"三件事上。
